## Purpose and scope

Amazon stopped answering the tracked-item checks, probably because it detects them as a bot. The user asks that Amazon pages be requested by a real web browser and that checks no longer happen at the same time every day, so that requests look like a person's.

Included: how tracked Amazon item pages are requested; when scheduled Amazon checks happen; a one-time restart of the Amazon items stopped before this change; files offered as downloads during an Amazon check (issue #217), also when the check is interrupted (issue #233); the wording of the server log line reporting that the browser cache could not be cleared (issue #240); the wording of step 4 of the Backend `Collect` steps in the technical specification about when the browser cache is cleared (issue #234, maintenance, no behaviour change).

Excluded: LeBoncoin items, which keep their current requests and schedule (08:00 and 20:00 by default); the failure count, stop, warning and restart rules ([Amazon request stop](../amazon-request-stop/functional.md)), which stay unchanged; price and second-hand offer detection; AI reviews.

Actor: the user who tracks Amazon items. Amazon is the external system.

Terms:

- **Amazon check:** retrieval of a tracked Amazon item's page: first check after add, scheduled check, **Refresh all prices**, **Refresh price**.
- **Real web browser:** a full web browser engine that loads and renders the page as it would for a person (page scripts, page resources, cookies), as opposed to a plain download of the page.
- **Morning window:** 06:00 to 09:00; **evening window:** 19:00 to 23:00. Times are in the schedule timezone (`Europe/Paris` by default).
- **Failure:** as defined in [Amazon request stop](../amazon-request-stop/functional.md): no usable Amazon answer.

### Specification wording (issue #234, maintenance)

Step 4 of the Backend `Collect` steps in `doc/specifications/amazon-human-checks/technical.md` says that the HTTP cache is cleared before the failure "with a 2xx response". The server also clears it when the browser recorded no response within the 1 s wait, as the TS-AMZ-HCHK-017 row and its Backend bullet already say: a response may arrive after the wait, so no response cannot be told apart from a late one. Step 4 must match them. No behaviour change: the server keeps clearing the cache in both cases, as today (FR-AMZ-HCHK-014).

- **FR-AMZ-HCHK-017** Step 4 of the Backend `Collect` steps of the technical specification says that, with a 2xx response or none, the HTTP cache is cleared first, says that a response may come after the 1 s wait, and refers to issue #217 and TS-AMZ-HCHK-017. Check: step 4 contains `with a 2xx response or none (a response may come after the 1 s wait), the HTTP cache is cleared first (issue #217, TS-AMZ-HCHK-017)`.
- **FR-AMZ-HCHK-018** No text of the technical specification still says that the cache is cleared only with a 2xx response, and the rest of step 4 keeps its meaning: the clearing also happens when the check is interrupted, and an interrupted `Page.navigate` clears the cache too (issue #233, TS-AMZ-HCHK-018–019). Check: `doc/specifications/amazon-human-checks/technical.md` no longer contains `with a 2xx response the HTTP cache is cleared first`; step 4 still contains `also when the check is interrupted` and `clears it too (issue #233, TS-AMZ-HCHK-018–019)`.
- **FR-AMZ-HCHK-019** Nothing else changes: the text of FR-AMZ-HCHK-001 to 016; in the technical specification, the TS-AMZ-HCHK-017 row, its Backend bullets and every other entry, apart from the lines that record the issue #234 change; the change records under `doc/changes/` of other issues; the files under `doc/todo/`, including `doc/todo/issue-217-r2-02.md`. The change's diff outside `doc/` is empty; `go vet ./...` and `go test ./...` pass, and the operator observes no change in the application.

## States and corner cases

- Item states and messages are unchanged (pending, active, retrieval issue, unavailable, stopped).
- A check that starts while a previous check of the same item is in progress is not duplicated (as today).
- The browser is never shown to the user and never needs user action; no Amazon login is used.
- Logs never contain tokens or session secrets (FR-AMZ-HUMAN-012).
- Deleting an item cancels its scheduled checks.
- In protected mode the windows and the one-time restart apply to the Amazon items of all users.
