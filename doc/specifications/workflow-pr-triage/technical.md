# Workflow PR comment triage: technical specification

Status: ready
Requirements: [functional](functional.md).

- **TS-WORKFLOW-TRIAGE-001** New stage 10 in `WORKFLOW.md` (and its overview row and the stage list `... pr-review, pr-triage, merge, complete`), role `.agents/roles/pr-review-triage.md`, template `templates/pr-triage.md`, and `AGENTS.md` step 10. Stage 9 no longer leaves fixes to the user.
- **TS-WORKFLOW-TRIAGE-002** Blocking criteria: a possible bug, a requirement or contract violation, a security or data risk, a broken build or test, or refactoring or unrelated work mixed into a feature PR. The reviewer's label is a hint, and a comment that is wrong is non-blocking, with the reason recorded.
- **TS-WORKFLOW-TRIAGE-003** Todo files are named `doc/todo/<YYYY-MM-DD>-<slug>.md` in the existing todo format, with a date prefix, and committed on the PR branch (or on a separate docs PR if it would exceed 500 lines). Todo-only commits need no re-review. Issues are created with `gh issue create`; a failure is recorded and reported, and the workflow continues.
- **TS-WORKFLOW-TRIAGE-004** Loop guard: if the same blocking comment is still open after 5 fix rounds, it is escalated to the user and the workflow stops. This prevents an endless run, since ai-dev runs have a 120-minute timeout.
- **TS-WORKFLOW-TRIAGE-005** Merge: stack order; parts with `--merge` so the next stacked PRs still apply, and the final or single PR with `--squash`, matching the repository's squash history on master. Every merge uses `--delete-branch`, so GitHub retargets the next part to the feature branch. The agent checks each part's base. Stage 8 cannot open the final PR (GitHub refuses a head with no commits beyond its base), so after all parts merge and the ancestor check (`git merge-base --is-ancestor`) passes, the agent creates it with `gh pr create --base master --head <feature branch>` and `Closes #<n>`, then squash-merges it. `pr-triage.md`, with the triage decisions and the planned merge order, is committed to the last PR branch with `Refs: #<n>` before the first merge, so it reaches `master` with the squash; record-only commits need no re-review. Merge results, merge failures, the deploy run, and later todo or issue outcomes are reported only on the originating issue and in the final run report, never committed after branches are deleted. A failed merge is reported and stops the merging. `@claude` fix runs also end in triage, so they can merge automatically. A push made with `GITHUB_TOKEN` does not trigger workflows, so the agent runs `gh workflow run ci-deploy.yml --ref master`. ai-dev gets `actions: write`, and allows `gh issue create`, `gh pr merge` only as `gh pr merge * --merge --delete-branch` and `gh pr merge * --squash --delete-branch`, and exactly `gh workflow run ci-deploy.yml --ref master`.
- Frontend, backend and API: not affected.
- Verification: a YAML parse, `git diff --check`, and a consistency grep. This change's own PR (#55) is then taken through stages 9–10.
