# Blocking review comments (round 1)

## R1-01 `internal/service/service.go:547`

skipScheduledCheck only asks whether `now` is inside *some* Amazon window today (`inAmazonWindow(now)`). It does not ask whether `now` is inside the window the item was due in. TS-AMZ-HCHK-009 says: "A due Amazon item found outside its window (+15 min grace) ... is redrawn for the next window without a request". Example: an item due at 08:30 while the application is down from 08:20 to 19:05, or an item due three days ago with a restart at 07:00. Both are checked as soon as the scheduler starts (RunScheduler calls collectDue immediately), because now is in a window. Every overdue Amazon item is then checked back to back in one pass at start-up, with only the 5–60 s pauses between them. That is the batched, bot-like pattern that FR-AMZ-HCHK-005 removes. Fix: compare the due time with now, not just now. For example, let DueIDs (or a variant) return next_check_at, and send the check only when `now` is in the same local window as the due time (between that window's start and its end + amazonWindowGrace). Otherwise redraw with nextAmazonCheckAt(now) and log 'missed its window'. Add a test with a due time in the morning window and now in the evening window: it expects no request and a redraw.

Triage: Confirmed: skipScheduledCheck (internal/service/service.go:547) only tests inAmazonWindow(now), never the window the stored next_check_at belonged to. After downtime across a window (e.g. due 21:00, restart at 07:00), collectDue sends every overdue Amazon item in one start-up pass. That breaks TS-AMZ-HCHK-009 ("outside its window") and FR-AMZ-HCHK-005 (items not checked together in one run), and it is the batched pattern the issue blames for the bot detection.

## R1-03 `internal/store/amazon_requests.go:57`

The one-time migration clears next_check_at only for *stopped* Amazon items. Amazon items that are not stopped at upgrade time keep the next_check_at written by the old code: the shared configured time (08:00 or 20:00 by default, the same instant for every item). The service only redraws NULL times (scheduleUnscheduledAmazonItems), and collectDue accepts 08:00/20:00 because both are inside a window. So the first scheduled Amazon check after the upgrade still runs at the configured time, with all those items together in one pass. That contradicts FR-AMZ-HCHK-004 ("The configured check times ... no longer apply to Amazon items") and FR-AMZ-HCHK-005 ("items are not checked together in one run") for that first window. It happens to any item restarted by Refresh price or added before the upgrade. Suggested fix: inside the same guarded migration, unset next_check_at for every Amazon item (`UPDATE items SET next_check_at = NULL WHERE platform = 'amazon'`). Keep clearing the stop and resetting the count only for stopped items. Every Amazon item then gets its own draw at the first start. Update the TS-AMZ-HCHK-010 text and TC-027, which currently asserts that the old next check of a non-stopped item is kept.

Triage: Confirmed: restartAmazonItemsOnce (internal/store/amazon_requests.go:57) unsets next_check_at only for stopped items, and scheduleUnscheduledAmazonItems redraws only NULL times. Non-stopped Amazon items (restarted by Refresh price or added after the stop) keep the old shared 08:00/20:00 time. collectDue accepts that time because it is inside a window, so they are all checked together at the configured time. That breaks FR-AMZ-HCHK-004 and FR-AMZ-HCHK-005 for the first window after the upgrade and risks stopping the items again right after the one-time restart.
