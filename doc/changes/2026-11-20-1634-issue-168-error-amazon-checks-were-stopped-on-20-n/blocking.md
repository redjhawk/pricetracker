# Blocking review comments (round 2)

## R2-01 `internal/service/service.go:301`

A scheduled check skipped while the item was stopped can still run later, right after a Refresh price restarts the item. RefreshItem no longer writes next_check_at for Amazon items. amazonGate.do -> store.ClearAmazonStop clears only amazon_stopped_at. So a restarted item keeps the due time it had while stopped. Example: the item is due at 07:00. All items are stopped at 06:30 (5 failures), so DueChecks excludes it at 07:00. At 07:30 the user's Refresh price succeeds and restarts it. At the next 30 s tick DueChecks returns the item with DueAt 07:00. inDueAmazonWindow(07:00, 07:31) is true because both are in the morning window, and the item is no longer in flight. collectDue therefore sends a second browser check of the same item seconds after the manual one. That breaks FR-AMZ-HCHK-008 / FR-AMZ-STOP-004 ("Stopped items are skipped at their scheduled time"). It is also the back-to-back pattern this issue removes. Before this PR, RefreshItem moved next_check_at forward, so this did not happen. TC-032 only covers the tick that lands while the refresh is still running. Suggested fix: when an Amazon item is restarted (a manual check clears its stop) and its next_check_at is already past, set next_check_at = nextAmazonCheckAt(now). For example: in RefreshItem, for an Amazon item whose stored next check is <= now (only possible for a stopped item), store nextAmazonCheckAt(now). Or do it in the gate's restart path. A due time that is still in the future stays unchanged, as FR-AMZ-HCHK-007 requires. Add a service test: due 07:00, stopped 06:30, Refresh price at 07:30, collectDue at 07:31 -> exactly 1 check and the next check is in the evening window.
