# Blocking review comments (round 1)

## R1-01 `src/components/PurchaseGoalChoice.tsx:49`

In free-text mode, typing keeps `value.option` as is, so on a details page of an item without a goal the draft becomes `{ option: none, text: "Office" }`. If the component then switches to choice mode while the user is still editing (for example, polling brings in a goal set from another tab, and `withGoal` makes the list non-empty), the typed text is hidden under "No goal". `goalToSave` then returns "", and **Save goal** is enabled because "" differs from the new goal, so a click would clear the goal instead of saving what the user typed. This breaks FR-GOAL-CHOICE-014 (the saved goal is the text in the field) for that transition. Fix: in free-text mode, when the option is "none", map typing to `{ kind: "new" }`, e.g. `onChange({ option: value.option.kind === "none" ? { kind: "new" } : value.option, text: event.target.value })`. `goalToSave` returns the same result in free-text mode, and a later switch to choice mode shows "New goal" with the typed text.

Triage: Confirmed: App.tsx:211-227 polls getItem while an AI review runs, so `goal` can change while PurchaseGoal is dirty. withGoal then makes the list non-empty, the draft `{option: none, text: "Office"}` switches to choice mode with the typed text hidden under "No goal", and Save (enabled because "" !== goal) clears the goal instead of saving the typed text. This is a real data-loss bug, and the one-line fix in PurchaseGoalChoice.tsx:49 (map typing under "none" to "new") removes it.

## R1-02 `internal/service/purchase_goal.go:24`

FR-GOAL-CHOICE-006 and the user's answer Q-8 ask for alphabetical order. `strings.ToLower` followed by a byte comparison is not alphabetical as soon as a goal starts with a non-ASCII letter, which is likely for a French LeBoncoin user. For example, "écran pour bureau" sorts after "zoom photo", and "Ordinateur" vs "Œuvre" does not follow the alphabet either. The `compareGoals` mirror in `src/purchaseGoalChoice.ts` has the same problem, and `API_SPECIFICATION.md` ("Order") specifies it. Suggested fix: compare with a Unicode collation in the service, e.g. `golang.org/x/text/collate` with `collate.IgnoreCase` (and optionally `IgnoreDiacritics`), keeping the exact-text tie-break for determinism. Then update the API order rule and drop the client-side re-sort in `withGoal`, appending the item's goal and letting the next reload order it, or sort with `localeCompare`. Add a test case with an accented first letter. If the byte order is kept on purpose, the functional spec should state that accented letters sort after `z`.

Triage: FR-GOAL-CHOICE-006 (user answer Q-8) requires alphabetical order, case ignored. internal/service/purchase_goal.go:24-29 and compareGoals in src/purchaseGoalChoice.ts:34-39 compare lower-cased bytes, so a goal starting with an accented letter ("écran") sorts after "zoom". For a LeBoncoin (French) user that is a realistic unmet requirement. The API order rule and the tests (TC-001 uses ASCII only) need to change with the fix.
