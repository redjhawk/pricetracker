# Blocking review comments (round 1)

## R1-01 `API_SPECIFICATION.md:706`

The contract (and FR-HTTP-TMO-001) says a request not fully received within 15 s gets 'no response, and the request is not handled (nothing saved or started)'. abortLateBodies can only enforce that when the handler reads the body. net/http calls the handler as soon as the headers arrive, and endpoints that take no body never read it: `POST /api/v1/items/refresh`, `POST /api/v1/items/{id}/refresh`, `POST /api/v1/items/{id}/ai-review` and `DELETE` (server.go:94-129). Failure scenario: a client sends `POST /api/v1/items/I1/refresh` with `Content-Length: 10` and the body one byte per second. RefreshItem starts at once. When the handler returns, net/http tries to discard the unread body before writing the header, hits the 15 s read deadline, and still sends the 202 with `Connection: close` at about 15 s. So the work is started and a response is sent, which is the opposite of the documented row. Suggested fix: document it, with no code change. Write that the 15 s 'not handled' guarantee covers endpoints that read a request body, and that endpoints without one are handled once the headers arrive. Change this row and FR-HTTP-TMO-001 / UC-HTTP-TMO-001 the same way. If the stricter behaviour is wanted, refusing a non-empty body on body-less endpoints would be a functional decision for the user.

Triage: Confirmed: the refresh, single refresh, AI review and DELETE handlers (server.go:94-129, 143+) never read r.Body, so abortLateBodies never sees the deadline. net/http's post-handler discard of the unread body (on the original body, not the lateBody wrapper) runs into the 15 s read deadline, and the 202 is still sent with Connection: close after the work has started. That contradicts the API_SPECIFICATION.md row and FR-HTTP-TMO-001 ('not handled, nothing saved or started'), so the documented contract is not met.

## R1-02 `API_SPECIFICATION.md:705`

This row says that when the request headers are not received within 5 s, 'The connection is closed; no response.' That is not what Go does, and the test admits it. testSlowHeaders (http_server_limits_test.go:584-588) accepts Go's plain `HTTP/1.1 400 Bad Request`. bufio.Reader.ReadLine returns the partial request line with a nil error when the deadline fires, so textproto parses a malformed line and net/http answers 400. TC-012 (testcases.md:186, 'closed ... with no response') says the same as this row, so the documented contract and the test case contradict the behaviour the test asserts. Suggested fix: change the row to say the connection is closed with no response, or Go's plain-text `400 Bad Request` when part of a request line has arrived. Note it with the 431 bullet as a second non-JSON answer from net/http, and align TC-012's expected result.

Triage: Confirmed: bufio.Reader.ReadLine returns a partial request line with a nil error when the 5 s header deadline fires, so net/http answers its plain '400 Bad Request'. testSlowHeaders (http_server_limits_test.go:584-588) accepts that answer, but the API_SPECIFICATION.md row ('no response') and TC-012 ('with no response', zero bytes) say otherwise. The contract added in this PR and its test case contradict what the test asserts.
