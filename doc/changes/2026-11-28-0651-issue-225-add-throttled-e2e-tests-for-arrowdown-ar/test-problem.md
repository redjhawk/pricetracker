# Test problem (issue #225, review round 1)

The locked tests TC-001 and TC-003 (#225) in `tests/leboncoin-session-settings.spec.ts` (lines 1121, 1144) and TC-002 and TC-004 (#225) in `tests/app-information.spec.ts` (lines 289, 318) cannot fail when `handleTriggerKeyDown` in `src/components/AppMenu.tsx` handles only Escape. The issue's only acceptance check, testcases.md (TC-001 – TC-004, "fails without the fix") and functional.md (References, issue #225) require that they do. Blocking review comments R1-01 and R1-02 ask for exactly this fix, and only the tests stage can make it.

Cause (tests-note.md): `page.keyboard.press` resolves only after the renderer has handled the key. React handles the opening Enter as a discrete event and Carbon's focus effect has already moved focus to **Information** when the arrow key is sent, even at CPU rate 6. The arrow keydown therefore never reaches the trigger, so `focusEntryFromTrigger` never runs. In TC-004, Carbon's own ArrowUp from Information wraps to Log out, the same final state as the trigger branch.

Needed change (tests stage, from R1-01): make the arrow keydown reach the trigger while the menu is open but before Carbon moves focus. For example, in one `page.evaluate`: open the menu (`trigger.click()` or dispatch the opening keydown), wait one microtask so React commits the open menu, then `trigger.dispatchEvent(new KeyboardEvent("keydown", { key: "ArrowDown" /* or "ArrowUp" */, bubbles: true, cancelable: true }))`, and assert on `document.activeElement` afterwards. Keep CPU rate 6 and 5 rounds. Check by hand that each of TC-001 – TC-004 (#225) fails with the Escape-only handler and passes with the current one. If no technique reaches the trigger branch, escalate to the owner rather than keeping tests that cannot fail.

No production change is needed: the current `AppMenu.tsx` already implements FR-APP-MENU-009. FR-APP-MENU-009 (functional.md Status line) and TS-APP-MENU-007 (technical.md) are back at specified until the tests meet the check (R1-03).
