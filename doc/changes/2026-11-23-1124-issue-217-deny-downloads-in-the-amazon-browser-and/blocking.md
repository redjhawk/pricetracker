# Blocking review comments (round 1)

## R1-01 `internal/amazon/browser.go:446`

The HTTP cache is cleared only when `awaitDocument` found the navigated frame's 2xx Document response within its 1 s window. `awaitDocument` exists because Chromium can report the navigation error before the response event (technical.md, issue #186 section). The same spec also says 'A 2xx response that arrives after the error is also a failure'. In that case (`found == false`, the response comes late or is recorded under another frame id), the attachment body that the network stack already wrote to `<profile>/Default/Cache` is not cleared, and FR-AMZ-HCHK-014 ('no file from that response ... in the Amazon browser's persistent profile') is broken for that check. The tests cannot show this: the local fixture always delivers the response before the error. Suggested fix: clear the cache on every `errorText` path that does not return the error page, i.e. drop the `if found` guard (the clear stays best-effort and only logs). This fails closed and is simpler. The only cost is an extra cache clear after DNS or refused failures, which are already failed checks. Update the TS-AMZ-HCHK-017 bullet 'A navigation without a response ... unchanged' to match.

Triage: In `internal/amazon/browser.go:441-452`, `Network.clearBrowserCache` runs only when `awaitDocument` records the frame's 2xx response within 1 s. In that case the attachment body already in `<profile>/Default/Cache` is not cleared, so FR-AMZ-HCHK-014 (no file from that response in the persistent profile) can fail. Dropping the `found` guard fixes this with a harmless extra clear, and TS-AMZ-HCHK-017 (technical.md:362) must be updated to match.
